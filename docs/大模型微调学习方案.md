# 大模型微调学习方案（规划 · 复盘 · 踩坑总集）

> **本文档的来历**：最初写于开工前，是一份"两条实验线怎么做"的可行性评估。**现在两条线的全部实验已完成**，本文在保留原始规划的前提下刷新为「规划 + 复盘」双面文档：
>
> - **第二节**回答「当初的判断哪些对了、哪些被实测打脸」——这是本文最有价值的部分；
> - **第三节**是全部实验的实测成果总表，**第四节**是可迁移的方法论结论；
> - **第五节**是踩坑总集（现象 → 根因 → 解法），**第六节**是排障工具箱。
>
> **数字口径**：均来自本机实测。Qwen 线为 zhihu-kol 采样 **train 80 / validation 10 / test 10**（seed=42，与 LoRA 线同口径），基线 `eval_loss = 4.8659`（纯 base，10 条验证集）；BERT 线为 GLUE MRPC 全量（train 3668 / validation 408 / test 1725），基线 `macro_f1 = 0.406`（随机分类头"全预测多数类"）。表内数值统一以磁盘现存 checkpoint 的 `trainer_state.json` 为准；个别早期文档记录的数值（如 Prompt 线 4.3118）来自更早一轮重跑，差异约 ±0.02。

## 一、原始规划（存档）

> 整体规划：
> 1. Qwen3‑0.6B（Decoder‑Only 生成模型）：~~LoRA / QLoRA、量化实验~~ → 实际扩展为 **全量 SFT、LoRA、AdaLora、QLoRA、Prefix Tuning、Prompt Tuning、P-Tuning v2、4bit 推理、vLLM 部署**
> 2. BERT（Encoder‑Only 双向编码器）：~~Prefix‑Tuning / P‑Tuning / P‑Tuning‑v2 / Prompt‑Tuning~~ → 实际为 **全量微调、LoRA、AdaLora、P‑Tuning v2**
>
> 原方案的核心判断：**Qwen 侧只做 LoRA/QLoRA（"规避 peft 不支持 CausalLM 的 prompt 系"），BERT 侧主攻 P-Tuning v2（"必须用清华原始仓库，peft 的 PrefixTuningConfig 不能用于 BERT"）。**

**这两条核心判断最终都被证伪了**（见第二节）。但正是这个"先按旧认知划边界、再被实测推翻"的过程，构成了本仓库最大的学习价值——**它把社区文档里流传的一整类过时结论，逐个换成了本机可复现的证据。**

## 三、实验成果总表（实测）

### 3.1 Qwen3-0.6B 线（生成任务，基线 eval_loss = 4.8659）

| 方法 | 可训练参数 | 占比 | 终值 eval_loss | 相对基线 | 落盘产物 |
|---|---|---|---|---|---|
| 全量 SFT | 596,066,304 | 100% | **4.4278** | **-9.0%** | `model.safetensors` 1.19GB |
| Prompt Tuning | 16,384 | **0.0027%** | **4.3326** | **-11.0%** 🥇 | 65.6KB |
| Prefix Tuning（proj=True） | 59,843,584（训练时） | 10.0% | 4.4212 | -9.1% 🥈 | 3.67MB → 917,504 参数 |
| LoRA（r=8, α=16, 7 模块） | 5,046,272 | 0.84% | 4.5222 | -7.1% | 20.2MB |
| QLoRA（4bit NF4 + 同 LoRA 配置） | 5,046,272 | — | 4.5212 | -7.1% | 20.2MB |
| AdaLora（init_r=12 → target_r=8, α=24） | 7,571,760（训练时） | 1.26% | 4.6476（纯 CE） | -4.5% | 19.7MB |
| P-Tuning v2（proj=False） | 917,504 | 0.154% | **10.678** | **+119.4%** ❌ | 3.67MB |

**读法**：
- **"参数量"与"效果"在本仓库没有正相关**——16,384 个参数的 Prompt Tuning 打赢了 60M 参数的 Prefix 和 5.96 亿参数的全量 SFT。80 条数据下，**能训的参数越少，越不容易在 60~200 步内跑偏**。
- **P-Tuning v2 的 +119.4% 不是 bug，是论文前提不满足**：v2 的设计前提是 300M~10B 模型 + 大数据 + 大 lr（论文 MRPC 用 RoBERTa-large + prefix 长 100+ + lr 0.5~1）。0.6B + 100 条数据下它是**机制对照线**，被封存为"论文形态在小数据上不成立"的实证。
- **AdaLora 的 4.6476 是剥离正则项后的真值**：脚本里 Trainer 打印的是被正交正则污染的 4.87→4.65 表观值，逐条配对分析（10/10 改善，均值 6.4987→6.0456）给出的 **-7.0%** 才是它的真实学习量。
- **QLoRA 的 4.5212 不可与 LoRA 的 4.5222 横比精度优劣**（底座一个是 4bit NF4、一个是 bf16）。可比的是"相对基线的改善幅度"：两条线**都是 -7.1%**——即 **0.6B 这个体量上，4bit 量化的效果损失在本次实验里观测不到**。

### 3.2 BERT-base-uncased × MRPC 线（判别任务，基线 macro_f1 = 0.406）

| 方法 | 可训练参数 | macro_f1（最优 epoch） | 落盘产物 | 备注 |
|---|---|---|---|---|
| 全量微调 SFT | 110M（全部） | **0.833**（step 2100 峰值）/ 0.8133（末） | `model.safetensors` 438MB | 2751 步，lr=2e-5 |
| LoRA（r=8, α=16, q/k/v + classifier） | 546,822 | **0.8225**（ep3） | 2.21MB | 0.7515→0.8048→0.8225 单调上升 |
| AdaLora（init_r=12 → target_r=8） | 547,110 | 0.8009（ep2）/ 0.7995（ep3） | 2.22MB | 0.5525→0.8009→0.7995 |
| P-Tuning v2（16 token, proj=False, lr=1e-3） | 296,450 | 0.6731（ep4，训练 5 epoch） | 1.19MB | 含"全 1 退化解"拯救方案 |

**读法**：
- BERT（0.11B）在 6GB 卡上全量微调**完全可行**——2751 步量级只需几分钟（BERT AdaLora 线实测 2751 步 **4 分 33 秒**，SFT 同体量同量级）。**这是 Qwen 线做不到的**：0.6B + 15.2 万词表在 6GB 上只能靠 LoRA + 梯度检查点硬撑。
- 各线的 `best_metric`（由 `trainer_state.json` 记录）佐证了上表：SFT **0.8330** / LoRA 0.8225 / AdaLora 0.8009 / P-Tuning v2 0.6731。
- 判别任务的"效果"用 **macro_f1** 读，不要用 eval_loss。MRPC 正类占 67%，"全预测正类"的退化解 **f1=0.812 但 macro_f1 只有 0.406**——用 f1 选最优模型会选到偏科模型。

## 四、学习成果：值得带走的结论

### 4.1 论文名 ≠ 实现名（第一类"名实分离"）

| 论文方法 | 机制 | peft 配置类 |
|---|---|---|
| P-Tuning v1 | 输入层伪 token + LSTM/MLP 重编码 | `PromptEncoderConfig` |
| Prompt Tuning (Lester) | 输入层纯 embedding，无编码器 | `PromptTuningConfig` |
| Prefix Tuning (Li & Liang) | 每层注入 KV 前缀 + **MLP 重参数化** | `PrefixTuningConfig(prefix_projection=True)` |
| **P-Tuning v2** | 每层注入 KV 前缀，**去重参数化** | **`PrefixTuningConfig(prefix_projection=False)`（peft 默认）** |

- **"是哪个方法"最终由一个布尔超参决定**。Qwen 线上仅翻转 `prefix_projection`，结果从 **+119.4% / 全乱码** 变成 **-9.1% / 无乱码**；两条独立脚本连失败曲线都复刻到小数点后两位（10.66 / 10.6779）。
- 附带实证：`PromptEncoderConfig.__post_init__` 里有一行 `self.peft_type = PeftType.P_TUNING`，**你在构造时传 `peft_type="PROMPT_TUNING"` 会被静默覆盖**——`peft_type` 参数传了等于没传。

### 4.2 「起点中性」是第一判据

LoRA 的 `B=0` 初始化让"包装后未训练"**严格等价 base**；Prefix 系存在**机制性的起点罚金**：

| 形态 | 纯 base | 包装后未训练 | 罚金 |
|---|---|---|---|
| Prefix（10 条验证集 / bf16） | 6.4988 | **9.7949** | **+3.3** |
| Prefix proj=True（CPU / fp32 / 3 条） | 3.4265 | **8.4518** | **+5.03** |
| Prefix proj=False（CPU / fp32 / 3 条） | 3.4265 | **12.4707** | **+9.04** |

**罚金的来源被一组"绕过 peft 的原生 KV 注入"实验拆干净了**：

| 注入内容（单条样本） | loss |
|---|---|
| 无 prefix | 4.3575 |
| 注入 16 个**全零** KV | **8.7149（+4.36）** |
| 注入 N(0,1) 的 KV | 13.0068 |
| 注入 N(0,0.05²) 的小尺度 KV | 8.6979 |

**零 KV 剂量曲线（前缀长度 1 → 256）**：8.50 / 8.49 / 8.69 / 8.71 / 7.92 / 7.19 —— **① 只要 forward 里传了 `past_key_values`，哪怕内容全零，attention 行为就系统性劣化（+4.1 起步）；② 门槛与前缀长度基本无关，更长反而略好**。这条曲线一次排除了"softmax 概率被稀释"的假设，把责任定位到"传 cache 这个动作本身"。

### 4.3 可训练参数走哪条前向路径，决定了它与哪些训练设施兼容

| 方法 | 参数所在路径 | 能开 gc？ | 说明 |
|---|---|---|---|
| LoRA / AdaLora | 权重旁路（改 Linear） | ✅ | Qwen 侧需 `enable_input_require_grads()` 或 `use_reentrant=False` |
| Prompt Tuning / P-Tuning v1 | 输入拼接（`inputs_embeds`） | ✅ | 梯度经拼接点自然回传 |
| Prefix Tuning / **P-Tuning v2** | **KV 注入（`past_key_value`）** | ❌ **必须关** | gc 会把每层 `past_key_value` 置 `None` |

**这是全仓库最阴险的一类 bug：静默假跑。** 三种表现：

1. **Qwen 侧**：loss 恒定在 base 水平不动，仅伴随 25+ 条 `Caching is incompatible...` 警告刷屏——"能跑通、不报错、loss 看起来正常"，只有警告本身是破案线索；
2. **Qwen 侧另一种面孔**：同配置在部分组合下第一步 backward 就 `RuntimeError: element 0 of tensors does not require grad`；
3. **BERT 侧最静默**：**连警告都没有**。用梯度探针实测，3 个可训练参数只剩 **2/3** 有非零梯度（prompt embedding 的 `grad is None`），2000+ 步实际上只在训 classifier。

**判据**：警告消息里出现了对你**方法核心机制对象**（这里是 `past_key_value`）做修改的字样，它就**不是良性警告**。对照：SFT/QLoRA 开 gc 时的 `` `use_cache=True` is incompatible with gradient checkpointing `` 才是良性的——那是框架自己把 KV cache 关掉，一行即止，与你的参数在哪条路径无关。

### 4.4 lr 按"冻结彻底程度"重校

| 参数类型 | 代表方法 | 本仓库实际 lr |
|---|---|---|
| adapter 系（权重旁路） | **LoRA / QLoRA** | 脚本**未显式设置** → 吃 `TrainingArguments` 默认 **5e-5**（仍拿到 -7.1%，但明显偏保守） |
| adapter 系（显式调参后） | **AdaLora** | **2e-4**（调参前就是吃了默认 5e-5，见下） |
| 全量微调 | BERT SFT | **2e-5** |
| embedding / prompt 系 | Prefix / P-Tuning v2 / Prompt Tuning | **1e-4 / 1e-4 / 5e-3** |

**"冻结得越彻底，需要的步长越大"**：可训练参数越少、离输出越远，梯度信号越弱，adapter 系的 lr 直觉套到 prompt 系上会"学不动"——BERT 侧卡在"全预测多数类"退化解，Qwen 侧训练前后生成完全不变。

**反过来，adapter 系自己也可能吃了默认值而不自知**：AdaLora 线最大的一个坑就是 `TrainingArguments` **没写 `learning_rate`** → 吃默认 **5e-5**（全量微调量级），叠加 AdaLora 的有效缩放 `α/ranknum = 16/12 ≈ 1.33`（小于 LoRA 的 `16/8 = 2.0`），60 步下来 `lora_A` 的 RMS 与随机初始化几乎相同——**根本没学动**。显式设 `lr=2e-4` + 提到 10 epoch 后，CE 才从 +2.6% 翻转为 **-4.5%**。

> **一条实用习惯**：`learning_rate` 永远显式写出来，不要依赖默认值。默认值改一次版本就可能变，而"没学动"是个不会报错的静默故障。

### 4.5 "复用训练成果"是两种机制，不是一种模式（第二类"名实分离"）

| | LoRA / AdaLora / prompt 系 | **全量 SFT** |
|---|---|---|
| 训练时改什么 | 冻结主干，只训 adapter | **全部参数都在训** |
| `trainer.save_model(path)` 存什么 | 只存 adapter（几十 MB） | **完整权重**（Qwen 1.19GB / BERT 438MB + config + tokenizer） |
| 完成标志 | `adapter_config.json` 存在 | **`model.safetensors` 存在** |
| 加载方式 | `PeftModel.from_pretrained(base, path)` | **`AutoModelForCausalLM.from_pretrained(path)`** |
| 能否切回 base 做对比 | `disable_adapter()` 可用 | **不可能**——权重已被覆盖，**基线评估必须在重载之前完成** |

跨这两个世界复制脚本时，**判断文件、加载 API、显存账三件事都要跟着换**。SFT 复用分支还多一条：重载前必须 `del trainer_baseline, model` 释放旧引用，否则 6GB 卡上会同时存在两份 0.6B 权重。

### 4.6 混精匹配律：权重 dtype 决定 AMP 开关

**bf16 权重配 `bf16=True`（无 GradScaler）；fp16/fp32 权重才配 `fp16=True`（有 GradScaler）。** `torch_dtype="auto"`（拿回 bf16 权重）+ `fp16=True` 是自相矛盾的组合，实测在**第一步 `clip_grad_norm_` 就崩**：

```
NotImplementedError: "_amp_foreach_non_finite_check_and_unscale_cuda" not implemented for 'BFloat16'
```

**traceback 里出现 `grad_scaler.py` + `BFloat16` 字样即可秒判。** bf16 本来就不需要 loss scaling。

### 4.7 显存账与算力账（6GB 卡的定量认识）

**显存的大头不是参数量，是词表**。Qwen3-0.6B 词表 **151,936**，CLM 的 **loss 路径峰值 ≈ `bs × seq × 词表 × 10 B`**：

- `bs=1, seq=1024`：bf16 logits 0.6GB + CE 的 fp32 副本 1.25GB ≈ **1.9GB**；
- `bs=8`：2.5GB（bf16 logits）+ 5GB（fp32 上转）+ ~4.6GB（CE 内部）≈ **12GB** → 实测报错 `Tried to allocate 4.64 GiB`、`total capacity of 6.00 GiB`；
- 6GB 卡、seq=1024、词表 15.2 万时，**bs 上限约 2~3**。

**"eval 无梯度所以批量可以更大"是错的**：该论断只对激活/反向成立，**logits 与 CE 的显存与 batch 严格成正比**，而它们正是大头。

**算力账**：LoRA 是 **4ND**（≈2.4 GFLOP/token），全量才是 6ND（≈3.6）。LoRA 省的是"反向的权重梯度 dW"和优化器状态显存（Adam 从 2.4GB → 20MB），**前向 2ND 与反向激活梯度 2ND 一点没省**——这解释了"换 LoRA 后训练速度并没有快很多"。实测 1.33 s/it ≈ 5.0 TFLOPS ≈ 35~40% 利用率，属正常水平。

**优化优先级**：缩数据集 ≫ 修评估开销 > 降 `max_length` > 显存/吞吐微调。**时间 ∝ token 总量**——把训练集从 2.4 万条砍到 80 条，比所有软件优化加起来都有效。

### 4.8 评估方法论：本仓库最容易翻车的地方

1. **退化解检测器**：分类任务 `len(set(preds)) == 1` 就是"没学动"的硬信号，**比 loss 曲线可靠**（loss 微降可能只是偏置滑动）。BERT v2 线的定位即由此开始（混淆矩阵 `[[0,129],[0,279]]`）。
2. **配对分析**：10 条验证集下，不配对标准误 1.33 → 会得出"完全不显著"；**配对**（同一样本前后比）标准误 0.186、均值差 0.453 = **2.4 倍 → 显著**。样本间基线差异被消掉后，灵敏度高一个量级。
3. **输出里的标签结构由提示文本决定，与模型能力无关**。曾把数据集里**拼好的完整对话（含金标答案）**当生成提示，导致"模型生成的回答"其实是金标本身；也导致"生成到 `<|im_end|>` 不停"的假象——因为终止符出现在**输入**而非生成序列，且 `truncation=True` 从右截断时**第一个被切掉的正是答案末尾的终止符**。
4. **生成式评估三前提**：① prompt 只含指令不含答案；② greedy（`do_sample=False`）或固定 seed；③ 同批测试样本。缺一结论无效。另外 PEFT 模型生成前**必须 `model.eval()`**（Trainer 会把模型切回 train 模式，`lora_dropout=0.1` 会让 greedy 也不可复现）。
5. **英文评测管线对中文静默失效**：vendored `rouge-score` 的 `DefaultTokenizer` 只认 `[a-z0-9]`，对纯中文返回**空列表**——所有样本得 0，**不报错、不警告**。更糟的是"逐字加空格"的 hack **对汉字完全无效**（汉字不在字符集里，加不加空格都一样）。正确做法是给 `rouge.compute` 传字符级 tokenizer（`tokenizer=lambda s: list(s)`）。
6. **伪信号比零信号更危险**：修好之前各线 ROUGE"看起来有数字、多数还提升"（LoRA 0.0174→0.0478），实际全是拉丁字符（`<think>`、"One"、乱码词）与参考里偶见数字的**碰巧 LCS 重叠**——纯噪声，与生成质量零相关。
7. **指标方差 > 信号时果断弃用**。同一配置换精度就能从 0.0174 波动到 0.0441，比各线之间的差异还大。最终解读框架：**eval_loss（NLL，不经过分词）= 效果主指标；字符级 ROUGE 仅作辅助（0.10~0.14 是无重叠的常用字基线区，>0.2 才有参考价值，不做跨线比较）；预测类别数 = 退化解报警器；生成原文审读 = 信息量最大，肉眼不可省。**
8. **任何英文原生指标用于中文前，先做"正样本能否得非零分"的烟囱测试。**

### 4.9 AdaLora 的本质：一套互相约束的调度计划

**peft 不会自动做秩预算调度。不调用 `update_and_allocate()`，你的脚本就不是 AdaLora**，只是"秩 12 的三因子参数化 LoRA + 正交正则"。该方法内部做两件事：①重要性打分 `ipt = |p × p.grad|`（EMA 平滑 + 不确定性量化）；②按三阶段调度算 budget，用 `torch.kthvalue` 把最不重要的三元组的 `lora_E` 置 0。

- **触发时机必须是 `on_optimizer_step`**（`optimizer.step()` 之后、`zero_grad()` 之前）。网上常见的 `on_step_end` 写法在 transformers 4.55 下**必然 TypeError**——`zero_grad()` 已经把梯度置 None 了。也不能用更早的 `on_pre_optimizer_step`：在 `optimizer.step` 前 mask，紧接着的 Adam 更新会把刚置 0 的 `lora_E` 又推开（Adam 更新量与参数当前值无关）。
- **`total_step` 必须等于真实训练总步数**（peft 强制校验），`r` 参数**完全无效**（控制最终秩的是 `target_r`；且 `r=8` 恰好等于默认值，连 warning 都不触发）。
- **判据**：budget 前向打印应从 `init_bgt` 逐步降到 `target_bgt`（Qwen 线 2352 → 1568），`lora_E` 零值比例终值约 1/3。
- **训练中参数数量不变**（mask 不缩形，`resize_modules_by_rank_pattern` 在训练路径被官方注释禁用），**保存/加载时才真正缩形**（Qwen 线 7,571,760 → 4,916,768）。

### 4.10 极小数据 SFT 学到的是"格式与风格"，不是知识

- 训练 80 条后，Qwen 线学到的是 `<|im_end|>` 干净收尾、短答、`</think>` 闭合；**知识没学到**（生成"斯诺克三种开球方法：单手/双手/三手开球"是胡编）。
- **改善最大的恰是离群样本**：base 完全答不上的问答，CE 从 17.36→15.42、10.26→9.22（逐条配对）。**"知识没学到"是预期管理，不是失败。**
- **收益集中在第一个 epoch**（LoRA 线 epoch 1 拿走大部分提升）→ **想再涨要加数据，不是加 epoch**。
- **"重复坍塌"（同一句话循环 20 次）不是 bug**：贪心解码 + 小数据 LoRA 的典型病，采样可缓解，但**对比实验必须保持 greedy**。
- ROUGE 类指标天生度量"与参考的字面重合"，而 instruction 微调学的是**风格与分布**——两者本就弱相关。想让 ROUGE 真的涨起来，需要的是把任务改成"逼近特定参考"的形态（摘要/改写），那不是 zhihu 问答任务的语义。

### 4.11 全 1 退化解：七组对照实验（E1–E7）——"归因靠对照，不靠猜"的最佳范例

BERT × P-Tuning v2 线首次跑完的现象极具迷惑性：可训练参数 296,450（0.27%，与预期一致，**不是配置错误**）、eval_loss 0.6341→0.6149（微降）、**accuracy / f1 / macro_f1 与基线一字不差**、混淆矩阵 `[[0,129],[0,279]]`。

**先做合理性判定（三步）**：① 基线本身就是全 1（acc 0.684 = MRPC 验证集多数类占比 279/408，macro_f1 0.406 正是全 1 值）；② 训练后三指标与基线**完全相同** → 停在"随机分类头"退化解，loss 的 -0.02 只是把输出概率往类 1 轻推；③ MRPC 正类占 67%，**学不到判别信号时"全预测多数类"就是 loss 的局部最优**——这解释了 loss 为何不升反降。

| # | 配置（CPU / fp32 / batch16 / train 200~1500 条） | loss | acc | macro_f1 | 预测类别数 |
|---|---|---|---|---|---|
| E1 | **linear probe**：frozen BERT 只训 classifier，lr=1e-3 | 0.628→0.640 | 0.685 | 0.407 | **1** |
| E2 | **LoRA 对照**（r=8, q/k/v, lr=5e-4） | 0.716→**0.402** | **0.820** | **0.763** | **2** ✅ |
| E3 | v2 现状（proj=False, lr=1e-4） | 0.563→0.644 | 0.685 | 0.407 | 1 |
| E4 | proj=True + lr=5e-4 | 0.685→0.614 | 0.685 | 0.407 | 1 |
| E5 | v2 + **lr=1e-3**，3ep | 0.563→0.683 | 0.640 | **0.627** | **2** ✅ |
| E6 | v2 + **lr=3e-3**，3ep | 0.563→0.638 | 0.670 | **0.646** | **2** ✅ |
| E7 | **proj=True + 小尺度 0.02 初始化 + lr=1e-3**，3ep | 0.588→**0.435** | **0.770** | **0.665** | **2** ✅ |

**这七组实验各自排除了什么**：

- **E1（决定性）**：连"不包装、只训 classifier、lr=1e-3"都全 1 → **「冻结主干 + 轻量分类头」这一类方法在 MRPC 上天然起步极慢**。这不是实现问题，是方法类属决定的天花板起点。**先跑 linear probe 下限**是判断"多少责任在方法、多少在任务本身"的标准动作。
- **E2**：LoRA 同条件轻松到 0.763/0.820。LoRA 能学**不是因为分类头**，而是**直接改 attention 权重（表示本身在适配）**——这就是"LoRA 工业主流 vs prompt 系学术为主"的机制解释。
- **E3**：复现退化解（v2 现状）。
- **E4**：proj=True + lr=5e-4 **仍然全 1** → **单靠重参数化不够**。
- **E5 / E6**：lr 提到 1e-3 / 3e-3 后**一步脱离全 1** → **lr 是决定性变量**。
- **E7**：proj=True + 小尺度初始化 + lr=1e-3，loss 才出现实质下降（0.588→0.435），学习曲线健康。

**结论——两个必要条件，缺一不可**：**「重参数化 + 足够步长」**。BERT 侧单开 proj=True 不够（E4），单加 lr 也能脱困但离最优差约 2 个点（E5/E6）。

**与论文的差距要说清楚**：v2 论文的 MRPC SOTA 条件是 RoBERTa-large/BERT-large + prefix 长度 100+ + lr 0.5~1（Adafactor）+ 精调。**`bert-base` + 1e-4 量级的 lr 差了好几个数量级**——所以"v2 在本仓库打不过 LoRA"完全在预期内，它是一条**机制对照线**，不是效果线。

**两条拯救路线，脚本落地的是方案二**：

- **方案一（E7 抄法，实测最优，未落地）**：`prefix_projection=True` + 紧随 `get_peft_model` 之后做**小尺度初始化** `model.prompt_encoder["default"].embedding.weight.normal_(0, 0.02)` + `lr=1e-3` + 5 epoch。**代价**：可训练参数从 0.30M 涨到 **9.9M（`encoder_hidden_size=512`）~ 14.8M（取 peft 默认 = `token_dim`=768）**，约为 BERT 总参数的 9%~13%，适配器几十 MB，显存 +100~200MB。
- **方案二（已落地在 `test_PTuningV2_bert.py`）**：`prefix_projection=False` 不动，只把 `lr` 提到 **1e-3**、epochs 提到 5（`load_best_model_at_end` 按 macro_f1 保最优）。保住 v2 论文纯度，此时 macro_f1 达 **0.6731**，距 E7 约 2 个点（但显存/参数代价小得多）。

> **命名定位建议**：`test_PTuningV2_bert.py` 保持 v2 纯度（方案二）；若想要方案一的最强效果，**另建 `test_Prefix_bert.py`**（BERT 侧正好缺 Prefix 线），不在 v2 脚本里开 `projection`。落地原则与 Qwen 侧对称：**Prefix = 效果线 / P-Tuning v2 = 机制线**。

## 五、踩坑总集（现象 → 根因 → 解法）

> 按"危险程度"排序：**静默失效 > 崩溃报错**。崩溃会立刻暴露，静默失效会让你在错误结论上建三层楼。

### 5.1 静默失效类（最危险：不报错，但实验结论已经失真）

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | loss 看起来正常，但"prompt 部分 mask 成 -100、只对回答算 loss"**完全没生效** | `DataCollatorForLanguageModeling` 的 `mlm=False` 分支里 `labels = batch["input_ids"].clone()` **无条件覆盖**数据集自带的 labels | 换自定义 collator。**修前修后的 eval_loss 不可比，必须用新代码重跑** |
| 2 | 生成"停不下来"，跑满 256 token 不闭合 | `pad_token == eos == <\|im_end\|>` → collator 把 `labels == pad_token_id` 的位置全置 -100，**停止符的监督被抹掉** | 自定义 collator 不再抹 `<\|im_end\|>` |
| 3 | Prompt 系训练"假跑"：loss 恒定不动（Qwen）／**连警告都没有**（BERT） | `gradient_checkpointing` 把每层 `past_key_value` 置 `None` → KV 注入的可训练参数脱离计算图 | prompt 系**必须 `gradient_checkpointing=False`**。用梯度探针自检：`model.prompt_encoder["default"].embedding.weight.grad is None` 即假跑 |
| 4 | AdaLora 能跑通、无报错，但秩预算"从未衰减" | **peft 不会自动调度秩**，必须自己调 `update_and_allocate()` | 写 `TrainerCallback`，在 `on_optimizer_step` 里调用 |
| 5 | 改了 `r` 却毫无反应（若无其事） | AdaLora 里 `r` 完全无效；`r=8` 恰好等于默认值 → **连 warning 都不触发** | 删掉 `r`，用 `target_r`（最终秩）/ `init_r`（初始秩） |
| 6 | QLoRA 的"复用实验"其实一直加载的是 LoRA 线的权重 | 4 处目录没改名 → `has_adapter` 误判。**适配器与 base 是否量化无关**（形状只看 r/target_modules），LoRA 的 adapter 能直接套在 4bit base 上 | 目录、`lora_save_path`、`has_adapter` 路径三处同步改名 |
| 7 | 训练全程**一次 eval、一个 checkpoint 都没有**，TensorBoard 空的 | `eval_steps=200` / `save_steps=100` 是按 80 万条全量口径设的，采样后全程只有 **60 步** | 改 `eval_strategy="epoch"` + `save_strategy="epoch"` |
| 8 | TensorBoard 里只有 eval_loss，**train_loss 一条都没记** | `logging_steps` 默认 **500** > 全程 200 步，从不触发 | 显式 `logging_steps=20`（与 eval 对齐）。**历史数据无法补救** |
| 9 | 改了 `tokenize_func` / `max_length`，结果毫无变化 | `.map(cache_file_name=...)` **只看文件是否存在、从不校验指纹** | 删对应 `.arrow` 缓存。**真正的风险方向是"函数变了、缓存还在 → 静默加载旧数据"，日志毫无异常** |
| 10 | 训练中途 `loss=NaN` | `truncation=True` 从右截断，user 部分本身超长 → 回答被完全切掉 → labels 全 -100 | 过滤超长样本或在 collator 里跳过全 -100 样本 |
| 11 | 前向崩溃（labels 与 input_ids 形状错位） | `tokenized_user` 截到 4096 而 `tokenized_full` 截到 1024 → `label[:user_len] = [...]` 在 Python 切片赋值语义下**把 1024 长的 label 撑长到 1100** | 两处 `max_length` 必须一致（都 1024） |
| 12 | ROUGE-L 全为 0（SFT 线），或全为噪声（其他线） | vendored rouge 的英文分词对中文返回空列表；"逐字加空格"的 hack 对汉字无效 | 传字符级 tokenizer；并用字符级基线区（~0.10-0.14）解读 |

### 5.2 崩溃类（报错明确，但根因往往在别处）

| # | 报错 | 根因 | 解法 |
|---|---|---|---|
| 13 | `RuntimeError: element 0 of tensors does not require grad and does not have a grad_fn` | 冻结主干 + **reentrant** 检查点：段输入没有 `requires_grad=True`。**伴随 `None of the inputs have requires_grad=True` 是根因级直接证据** | ① `model.enable_input_require_grads()`；或 ② `gradient_checkpointing_kwargs={"use_reentrant": False}`。**gc 本身是 6GB 卡的 OOM 规避参数，不能删** |

| 15 | `ValueError: AdaLoRA does not work when total_step is None` | peft 强制校验；还有 `tinit < total_step - tfinal` 的调度不等式 | `total_step` 填**真实总步数**；改 `num_train_epochs` 必须同步重算 |
| 16 | `TypeError: unsupported operand type(s) for *`（在 `update_and_allocate` 里） | 用了 `on_step_end`，而 transformers 4.55 的 `zero_grad()` 在它之前执行，`p.grad` 已是 None | 改用 `on_optimizer_step` |
| 17 | `AttributeError: 'Qwen3ForCausalLM' object has no attribute 'trainable_adapter_name'` | `from_pretrained` 默认 `is_trainable=False` → `_freeze_adapter` → `trainable_adapter_name` **从未被设置**，而 `AdaLoraModel.forward` 只要 loss 非 None 就**无条件访问**它。崩溃三要素：**纯加载模式 + AdaLora + 带 labels 的 forward** | 加载分支传 `is_trainable=True`。`disable_adapter()` 和 `orth_reg_weight=0` **都绕不开**（前者关不掉包装层 forward，后者 peft 直接 raise） |
| 18 | `ValueError: Cannot set a prompt learning adapter to trainable when loading pretrained adapter.` | `PeftModel.from_pretrained` 对 prompt learning 系直接 raise（其 checkpoint 存的是**编码后的最终 prompt embedding**，不含重参数化网络，无法续训） | prompt 系**禁止传 `is_trainable=True`**。这行是从 LoRA 脚本复制来的（LoRA 不是 prompt learning，那里合法） |
| 19 | `NameError: name 'trainer' is not defined` —— **首次训练能跑通、二次加载必崩** | `training_args`/`trainer` 被定义在 `else:`（训练分支）**内部**，而 `trainer.evaluate()` 在分支外、两种模式都执行 | 两块定义**整体去掉一层缩进**移到模块顶层。**`test_Lora_bert.py` 同病** |
| 20 | `RuntimeError: size mismatch for ...lora_A.default`（AdaLora 训练末尾） | `load_best_model_at_end` 与 AdaLora 的 `rank_pattern` 演化**不兼容**：内存里是终态 pattern，而 best checkpoint 是**较早 epoch**、形状不同；peft 的 `load_adapter` 对已存在的 adapter 名不读 checkpoint 的 config | `load_best_model_at_end=False`（语义反而更对——`tfinal` 定秩段本就是在**最终秩结构**上精调）。要 best epoch 就用**干净的 base** 重新 `from_pretrained(base2, best_ckpt, is_trainable=True)` |
| 21 | `TypeError: PrefixTuningConfig.__init__() got an unexpected keyword argument 'encoder_hidden_size'`（v2 形态） | `encoder_*` 参数**只在 `prefix_projection=True` 时存在/有效** | v2 形态删掉 `encoder_hidden_size` / `encoder_num_layers` / `encoder_dropout` |
| 22 | `NotImplementedError: "_amp_foreach_non_finite_check_and_unscale_cuda" not implemented for 'BFloat16'` | 权重 bf16（`torch_dtype="auto"`）+ `fp16=True`（启用 GradScaler），而 bf16 从不需要 loss scaling | `fp16=True` → `bf16=True` |

| 24 | `NameError: name 'model_lora' is not defined` | 从别的脚本复制后变量名没改全（本脚本叫 `model_trained`） | 改脚本后 `grep -n "model_lora\|LoRA" 新脚本` 扫残留 |

### 5.3 口径与基准类（数字对不上，其实是谁跟谁比的问题）

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 25 | 复用模式下"微调前后 -0.0%"，而首训是 -7.1% | **PEFT 是原地改造传入的 model**（`from_pretrained` 和 `get_peft_model` 都返回**就地改造后的同一个对象**），而"包装前基线"的代码块**物理位置在包装之后**——注释写着"包装前"但代码顺序反了 | 把基线块整段移到包装之前。**"包装前/包装后"的语义只能由代码物理位置保证，不能靠注释** |
| 26 | AdaLora 表观 eval_loss 反而 **+13.7%** | `AdaLoraModel.forward` 对**任何**带 labels 的前向无条件加正交正则项（默认权重 0.5）。分解后 **81% 的增幅是正则**，CE 真实变化只有 +2.6% | 用 `eval_loss - R` 还原 CE；**诊断不必加载模型**——直接从 `adapter_model.safetensors` 算 `R = 0.5·mean(‖AAᵀ−I‖_F + ‖BᵀB−I‖_F)` |
| 27 | 基线与微调后差 0.0006，方向不定 | `training_args_baseline` 漏了 `bf16=True` → 两个 Trainer 走不同的 autocast 数值路径 | 两条 Trainer 的精度参数必须对齐 |
| 28 | QLoRA 与 LoRA 的 eval_loss 谁高谁低 | **跨精度线的绝对数值不可横比**（4bit NF4 vs bf16 底座） | 只比"微调后减基线的相对幅度"，或本线内部前后对比。**每条线要记录自己的基线锚点数值** |
| 29 | 判别任务基线只有 eval_loss，没有 acc/f1 | baseline Trainer 漏传 `compute_metrics` | 补上。判别任务上"微调前后 macro_f1 对比"比 loss 直觉得多 |
| 30 | 最优模型选得"偏科" | `metric_for_best_model="f1"` 在不平衡数据上虚高：**全预测正类时 f1=0.812，macro_f1 只有 0.406** | 改 `macro_f1` |
| 31 | 训练完想拿最优权重，发现最优 checkpoint **已被删除** | `save_total_limit=3` 只留最近 3 个，最优的 `checkpoint-140` 被轮换掉了 | `save_total_limit` 放宽 + `load_best_model_at_end=True`（注意坑 20：AdaLora 不适用） |

### 5.4 工程与命名类

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 32 | 不同实验的产物混进同一目录 | 跨方法复制脚本，4 处路径带着上一方法的语义（`output_dir` / `logging_dir` / `lora_save_path` / `has_adapter` 判断路径） | 全部正名。**改目录名时必须同步改 `has_adapter` 的路径判断**，否则误判为"未训练"重训一遍 |
| 33 | 产物与代码版本对不上，怀疑配置 | —— | `checkpoint-*/trainer_state.json` 保存着**当次完整超参快照 + `log_history`**，`cat` 一下即可考古，比猜可靠 |
| 34 | 注释与代码矛盾，误导后人 | 注释从别的脚本复制后只改了值、没改文案 | **错误注释比错误代码更害学习型仓库**。改配置时同步改注释 |
| 35 | 离线环境跑评估脚本报缺包 | 依赖 `rouge_score` / `nltk` 等可选包 | `try/except` 优雅降级，不阻塞主流程 |

### 5.5 当前遗留的注释错误（**建议清理**）

`test_Lora_bert.py:142-144` 与 `test_PTuningV2_bert.py:143-145` 的加载分支里，留着一段从 AdaLora 复制来的注释：

> `# ★ is_trainable=True 必须：evaluate/predict 的前向都带 labels，AdaLoraModel.forward 正则段访问 trainable_adapter_name...`

**但这两处的代码都已不传 `is_trainable`**——对 `test_PTuningV2_bert.py` 而言，**真按注释加回去会直接 `ValueError` 崩溃**（坑 18）。这正是"跨方法复制脚本时，加载分支比训练分支更容易踩雷"的活标本：注释带着上一方法的语义悄悄迁移。真实规则见下表。

**`is_trainable` 三分规则（由 peft 源码机制决定）**：

| 方法 | 加载适配器时 | 原因 |
|---|---|---|
| prompt learning（Prefix / Prompt / P-Tuning v2） | **不传**（默认 False） | 传 True 直接 `raise ValueError` |
| LoRA / QLoRA | 不传 | 传了无意义 |
| **AdaLora** | **必须传 `is_trainable=True`** | 否则 evaluate/predict 崩溃（坑 17） |

## 六、可复用的排障工具箱

### 6.1 判据清单（"怎么知道 X 出了什么问题"）

| 想知道 | 怎么判 |
|---|---|
| adapter 有没有学动 | 训练后 `lora_A` 的 **RMS** 是否偏离随机初始化 std（本例 0.020）。≈0.02 = 没动；0.028 = 真在学 |
| 新方法有没有"起点罚金" | **第一步先评"包装后未训练"的验证集 loss**（这一步一步定位了很多玄学问题） |
| 分类任务是不是退化了 | `len(set(preds)) == 1`，或看混淆矩阵是否只有一列非零 |
| 训练是否还有余量 | train loss 仍在明显下降且未远低于 eval loss → 有余量；**train loss ≪ eval loss（低 30%+）→ 已过拟合** |
| 瓶颈是不是算力 | 训练中另开终端 `nvidia-smi -l 1`，GPU 利用率**持续 >90%** 才是算力瓶颈（空闲时低占用不算数） |
| 系统内存吃满是否有害 | WSL 内 `free -h`：`used` 高才是真问题；`buff/cache` 高、`available` 充足是页缓存，**无害**（实测 42GB arrow 被 memory-map 后读满页缓存） |
| batch 上限估算 | **`loss 路径峰值 ≈ bs × seq × 词表 × 10 B`**，先套公式再留权重和激活余量 |
| 生成"停不下来" | 查三处：eos 是否出现在**输入**而非生成序列；padding/truncation 是否切掉了答案末尾的终止符；collator 是否把终止符监督抹成 -100 |
| 指标归零是哪坏了 | **先 `repr()` 打印生成原文**——分清"生成坏了"还是"评分坏了"，永远不要只盯着数字推理 |
| 基线数值是否可信 | **建立跨运行的锚点数值**（LoRA 4.8659 等）。任何一次运行的基线偏离锚点且无正当理由，就是基线出了问题——**基线数值是最灵敏的自检器** |
| 一段评估代码在评什么 | 看**执行时刻对象的状态**，不是变量名、不是注释（坑 25） |
| 警告是否良性 | 看它是否修改了你方法的**核心机制对象**（如 `past_key_value=None`） |

### 6.2 复现实验的自检清单（跨方法复制脚本时逐项问）

对 `PeftModel.from_pretrained` / `save_model` / 配置类的**每一个参数**问一句："这个参数在新方法下还有意义吗？"

1. 加载参数（`is_trainable`？）→ 查 5.5 的三分规则
2. `modules_to_save`（Qwen 侧删 `classifier`、BERT 侧必须留）
3. 路径与命名（4 处目录 + `has_adapter` 判断文件名）
4. 训练设施（gc 能不能开？`use_cache`？collator？）
5. lr 量级（adapter 系 1e-4 vs prompt 系 1e-3+）
6. 精度口径（`bf16` 有没有漏？两条 Trainer 是否一致？）
7. **二次运行（`has_adapter=True`）路径必须在开发时就跑通**——上述很多坑**只在首次训练成功后**才暴露
